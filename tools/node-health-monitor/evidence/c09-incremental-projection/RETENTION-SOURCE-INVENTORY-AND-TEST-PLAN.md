R4 §10 starts with **metrics 14 days, events 7 days, incidents 30 days, evidence 2 GiB**. Those are distinct classes: neither an M `process` observation nor a `witness_observations` archive row is automatically a metrics-series row, and this document assigns neither the 14-day metrics TTL by inference. Active unresolved incidents must not silently expire; older episode/raw-log replacement requires an explicit summary/hash plus `evidence_expired` semantics. A configured 2 GiB SQLite ceiling is a refusal/quota bound, **not cleanup**. Current table contents have no approved retention class mapping or deletion mechanism.

## Design boundary before any deletion code

1. Freeze a per-record retention classification/source manifest and an explicit reference graph: M global cursor boundary, Q retained original parents, every active fixed-W grant, packages, open/recovering incidents, and witness archive references. Unknown class or reference means **retain/refuse**, not guess a TTL.
2. Do not delete an M `observations` row merely because its event time is old. The current Q restart check requires exact original parent rows and the global-W anchor; M compaction needs a reviewed durable floor/anchor or summary protocol that both M and Q validate before any deletion. A Q-only orphan cleanup does not authorize M parent deletion.
3. Use one writer-owned, bounded transaction per maintenance batch: fixed maximum rows and serialized bytes, stable cutoff captured once, reference/pin check and deletion/tombstone together, rollback on any error. Commit a resumable progress marker only after the affected rows and required summaries are durable. Preserve SQLite WAL/FULL settings; a busy reader or checkpoint never justifies an unbounded wait or forced live `VACUUM`.
4. Preserve existing fixed grants and unresolved incidents under capacity pressure. If pins prevent bounded cleanup, refuse new diagnostic/query work with explicit monitoring-unavailable/capacity status; never make an old grant's evidence disappear or silently turn an incident green.
5. A backup/restore and old-binary compatibility plan must precede M/Q schema migration. The isolated integrity-revision prototype already changes M schema to v2, so retention migration must be ordered against that candidate rather than assuming deployed M has v2.

## Exact source-bound controls required before fixture cleanup

Use a new 0700 disposable test directory and disposable M/Q databases, with source SHA-256 and test binary SHA-256 recorded at start; never point cleanup tests at `/home/tomi` service DB paths. Each test must report pre/post table counts, IDs, global/Query watermarks, row hashes, WAL/main-file bytes, transaction result and reopened state. No cleanup implementation or fixture removal occurs until this plan is reviewed.

- **Reference refusal:** one active fixed-W grant references the oldest Q row and an M parent; one open incident references its evidence; one Q cursor anchors an old global M row. Crossing any configured retention cutoff must preserve all three exact originals and leave old grant/query and restart checks valid. Mutation removing each pin check must fail at the corresponding exact-ID assertion.
- **Class separation:** explicit approved metrics-series, event, resolved-incident and raw-evidence fixtures on both sides of their respective cutoffs; add M `process` and witness archive fixtures with *no approved TTL mapping*. Only classified, unreferenced eligible records may be removed; process/witness remain intact. No wall-clock reset may renew an old source age or silently reclassify it.
- **Bounded progress:** populate more than one maintenance batch with small and near-limit bodies; assert per-transaction row/byte cap, monotonic resumable cursor, one-writer/no-unbounded-wait behavior, and eventual permitted cleanup. A simulated busy reader/checkpoint and WAL growth beyond budget must refuse or defer without changing pins or claiming completion.
- **Crash windows:** inject failure before row changes, after some deletes/summaries but before commit, and after commit but before response/progress observation. Reopen and require all-or-nothing batch, idempotent replay, unchanged fixed-W parent/body/hash and explicit `evidence_expired` summary only when its original really was retired.
- **Capacity and recovery:** fill disposable M/Q toward the configured byte ceilings. Prove quota refusal is not counted as retention success; after permitted bounded maintenance, reopen/restart and show correct available space without a forced live vacuum. Restore a consistent backup with active grant/incident references, then verify the same eligibility and exact original identities. Test incompatible schema/old binary refusal explicitly.
- **Negative source changes:** tamper an M parent, global anchor, quarantine tuple, or Q origin while keeping timestamps old. Maintenance must fail closed, never erase the inconsistency as if it were expiry; the existing source-integrity and grant refusal controls must still fire.

Only after the two grant-path integration holds pass independent review should this inventory be used to create the separate retention worktree and implement a first, explicitly classified maintenance slice. The historic 5.735/6.128-second control reds, deployed-source status, and C09 RED/72-hour gate are unchanged.
