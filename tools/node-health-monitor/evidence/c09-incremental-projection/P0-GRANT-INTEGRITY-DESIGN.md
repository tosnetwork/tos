# C09 grant integrity and availability P0 disposition (design, not deployment)

This note reconciles the independent Starbridge review at `nhm/c09-raw-monotonic@85a4c90d6563aa9d4bfbf4b88984ce82fecf3ec2` (`live-data-version-31.jsonl` SHA-256 `1f92bbb70a876bb820833505397f29e7bc1e7c4fa67f9e51dc906a65d0de0a25`) with isolated `nhm/c09-grant-ledger-lock@48181d115832542f87f83e03cb55b51517788079`. **This is a candidate design and test inventory. No shared-branch integration or M/Q deployment follows from it; C09 remains RED.** The 95-page Data-release timing witness is a cost/lock witness, not grant availability acceptance.

## P0-1: Q lock check-to-create gap — closed only in isolation

The old grant handler released Q after `manager_cursor()` and later performed blocking `lock().create()` under Data. The isolated candidate retains one `try_lock` guard through both operations. Actual control-router tests require prompt 503 with no grant side effect while Q is held, normal 200 after release, and denial of a competing Q acquisition **after** cursor validation. Compiled old-lock mutations fail at those intended assertions. See `GRANT-LEDGER-LOCK-CANDIDATE.md` and `POST-CURSOR-Q-BARRIER.md`. This closes that particular lock/TOCTOU path in the isolated source; it does not bound SQLite fsync or the M source-head read, and the candidate is not integrated or deployed.

## P0-2: ordinary M writes starve new grants — observed, not fixed

Starbridge's stable read-only M connection observed 14 `data_version` advances and 39 global-head advances in 30 seconds with quarantine count zero. Our live-M/disposable-Q actual grant control got 1 HTTP 200 and 45 HTTP 503 across 46 seconds; all 45 stable refusals had **both** version mismatch and Q-cursor/M-head mismatch. A controlled disposable M/Q route test with only valid process appends every two seconds and no quarantine got 4 HTTP 200 and 27 HTTP 503 over 31 seconds. See `LIVE-M-GRANT-CADENCE.md` and `DISPOSABLE-M-ORDINARY-CADENCE.md`. Therefore neither dropping the version check alone nor describing the 95-page scan as an availability pass is valid.

Proposed successor: distinguish integrity-relevant changes from ordinary append-only observations. M would own a nonwrapping, transactionally incremented integrity revision, advanced for quarantine INSERT/UPDATE/DELETE and observation UPDATE/DELETE, **not** ordinary observation INSERT. The exact revision and retained-parent seq/hash/body/quarantine checks must be captured in one M snapshot and bound durably to Q's validated cursor, M database identity, and fixed source watermark. Missing/malformed revision, rollback or replacement is fail-closed. A new grant may freeze only a **previously validated** M snapshot watermark with the same integrity revision; later ordinary append-only head advancement would be reported as lag, not silently included in that grant. This changes today's “current M head equals Q cursor” policy and needs explicit review against the work order's same-snapshot grant rule and source freshness before implementation. No new lag threshold is assumed here.

Required changed-property controls before considering that design: ordinary INSERT advances head but not revision and leaves a grant for the already-validated fixed W eligible; same-W quarantine INSERT denies; ignored duplicate INSERT does not advance; quarantine UPDATE/DELETE and retained-parent UPDATE/DELETE deny; transaction rollback leaves revision unchanged; revision overflow, missing trigger/schema and database replacement refuse; crash/restart revalidates retained parents and exact revision. Run actual control-router grant cadence over several 15-second collector cycles plus read-only live-M/disposable-Q availability measurement. Do not infer success from isolated SQL trigger tests alone.

## P0-3: late quarantine and active fixed-W exposure — characterized, not fixed

`LATE-QUARANTINE-WINDOW.md` binds two actual controls: a matching quarantine committed after M retained-parent validation leaves an old fixed-W grant able to return the original process value/evidence until the next importer detects it; and a matching quarantine committed by a deterministic hook after the new grant's version/cursor check but before Q creation still permits one durable new grant. Two compiled diagnostic mutations fail at the precise HTTP 200-versus-503 assertions. The import interval is not a hard exposure bound: backlog, failure or missed scheduling may extend it.

A revision checked **once** during grant cannot close the final post-check/pre-create race, and a background importer/revision watcher alone cannot promise immediate revocation of an already-active grant. There are two coherent contracts to choose from before implementation:

- **Per-query source witness:** every query reads M's current integrity revision and database identity, failing closed on mismatch/unavailability, with the read as the query's ordering point. This is a local M read on the query path and may violate the existing cache-only boundary; it needs an explicit architecture ruling and measured 5-second/read-budget controls. A concurrent quarantine after the read may still commit before the HTTP response, so the ordering guarantee must be stated precisely.
- **Bounded-detection cache-only contract:** retain cache-only queries but set a finite monotonic validation lease on each grant, require successful renewal against M's revision, and reject queries when the lease is stale or the watcher is unavailable. This cannot promise immediate revocation; the maximum exposure must be an explicitly approved lease bound, tested under paused importer, backlog, process restart, quarantine between validation and creation, and failed renewal. No lease duration is chosen or authorized here.

Without one of those contracts, the truthful status is: new grants generally refuse a detected same-W quarantine, but there is a late-commit gap; active fixed-W grants can expose a quarantined cached parent until detection. Do not call this immediate fail-closed, a 15-second maximum, or C09 acceptance.
