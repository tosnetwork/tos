# Q terminal payload compaction candidate

Base: `node-health-monitor` `13288141f09ce5852907b67e018b4e90e5ef4eed`. This is an isolated candidate. It is not wired to a timer or deployed service, and its tests use disposable Q files only.

R4 §10 sets metrics 14 days, events 7 days, incidents 30 days and an evidence 2 GiB starting quota. It does not give raw Q grant, attempt or package rows a deletion age. The method therefore takes an explicit monotonic cutoff from a separately approved policy; it cannot infer a 7/14/30-day TTL from R4. The caller must pass a cutoff at or before the current `CLOCK_BOOTTIME` value. Only rows from the ledger's current boot and time namespace with `expires_ms <= cutoff` qualify. Old clock domains remain untouched until a separate boot-transition contract is reviewed.

The compaction transaction selects at most 16 expired runs and deletes their attempts, MCP binding and broker package. It marks each grant revoked and replaces its body with an empty terminal marker. The `query_grants.run_id` primary-key row remains permanently; the UUIDv4 is arbitrary and cannot be represented safely by a finite monotonic high-water mark. Recreating an old run ID still fails. Active fixed-W grants, their Q evidence and M parent origins are untouched. The existing 4096 lifetime grant-ID cap remains and will eventually refuse new runs. This candidate reclaims payload and the 65536 attempt / 8 MiB package budgets but is not a complete long-running retention solution.

`query_attempts.attempt_seq` uses SQLite `AUTOINCREMENT`; deleting attempts leaves `sqlite_sequence` in place. A new attempt must receive a strictly larger sequence after compaction and restart. Each run's attempts are checked against the existing 16-call budget before deletion; unexpected excess fails the whole transaction. `WAL` and `synchronous=FULL` are checked by the existing ledger open path. Deletes and terminal marking share one `IMMEDIATE` transaction: a failure before commit leaves all grant bodies, attempts, bindings and packages unchanged. Restart sees either the complete old rows or the compacted sealed rows.

The operator ledger view exposes only a redacted `terminal_payload_compacted` marker for a sealed ID. Repeat revoke is idempotent. All token and fixed-W authorization routes already exclude revoked rows. There is no live database invocation, M cleanup, Q evidence retention, checkpoint, VACUUM, or 72-hour acceptance in this slice.

## Full-row deletion design boundary

The production grant route currently makes a random UUIDv4-shaped `run_id`; `wire::uuid` checks syntax, not version or issuance order. Removing its last Q row would allow a caller of `QueryLedger::create` to present the same ID again. No fixed-size exact set can remember unbounded arbitrary old UUIDs. A future replacement can issue new IDs from a durable namespace plus monotonic serial, and atomically commit the next serial with the grant row. `create` must reject any generated serial at or below the durable high-water mark, even if its grant row was deleted. Existing random-ID rows remain legacy permanent seals. The route must stop generating an independent UUID before calling the ledger; the ledger must own allocation and insertion in one transaction. Fixed-W and token binding remain encoded in the new grant as today.

This handles process crashes and ordinary Q restart under SQLite FULL. It does not by itself handle restoration of an older Q backup: restoring an old issuance high-water mark can recreate an already issued ID. Exact rollback protection needs a separate non-rollback issuance floor or a reviewed restore protocol that changes the accepted issuance namespace and rejects old deleted IDs. Randomly rotating a namespace only makes collision improbable; it is not an exact replay proof. Until that authority and restore test exist, terminal grant rows cannot be deleted safely and the 4096-run lifetime cap must remain visible.
