# Explicit tick/tock execution context

`tick_context.py` independently authors 280 v16 contexts: two workchains, CP31
membership present/absent, absent/zero/tick/tock/both account flags, both explicit
API entry kinds, and seven program/state variants. CP45 is absent throughout.
The variants cover ACCEPT, THROW42, prior storage age, due payment, future
last_paid refusal, zero-balance compute skip, and storing the initial stack
balance after due-payment collection. They use public deterministic inputs.

Scheduling chooses which accounts should receive tick/tock transactions. Explicit
emulator/sandbox execution uses the supplied account and configuration; it must
not grant special-account privileges merely because the requested kind is tick
or tock. The native C API derives masterchain membership from the address and
specialness from CP31. Its flag admission is broader than the production
masterchain collator's scheduled population. These API cases do not establish
a deployed consensus fork or general permission to schedule arbitrary accounts.

The Rust executor uses its existing configuration predicate, validates storage
time before updating last_paid, and initializes the VM stack with the balance
after storage collection. Compute fees enter Transaction.total_fees. Aborted
execution restores selected account state while retaining fees. The action
phase receives the actual compute fee, as ordinary execution already does.

Each implementation runs independently in a supervised subprocess, retaining the
original config/full ShardAccount and raw result before comparison. Authored
assertions first check native description kind, storage/compute/total fees,
exact gas and limits, exit/skip/abort, balance, last_paid and logical time. Storage
fees are derived from the fixture's actual CP18 prices and advertised counters;
gas fees use independent scalar rules. The expected Account is constructed from
that input/program and those rules; its root and the transaction-bound
ShardAccount root are checked independently. Explicit zero tick/tock flags
canonicalize to absence in the output StateInit. No production account metadata
is normalized and no native result field is copied into Rust.

Both raw Transaction/Account/ShardAccount roots and every ordered observation
must then agree. Missing, extra, reordered, both-side wrong or truncated results
fail. Future-time errors must reach the storage phase and emit no output; an
arbitrary worker failure does not count as a valid refusal. Reports are capped
at 1 MiB before JSON parsing. Input is generated by a fixed 280-case matrix,
not an unbounded external row stream. Existing REL-02 supervision enforces wall,
CPU, address-space and file limits and cleans up failure/cancellation paths.

`test_tick_context.py --artifacts DIR` corrupts actual result rows and deletes
workflow obligations, proving independent native assertions and the ordered
comparison can reject wrong outcomes. Additional retained controls actually
revert privilege derivation, flag admission, fee accumulation, last_paid order,
abort fee retention and initial stack balance in Rust, then restore green.
The epoch workflow executes this gate in both architecture lanes and compares
full native/Rust outcome transcripts in its final job.

Native behavior is unchanged. TOS `emulator/emulator-extern.cpp` matches fetched
upstream `857b8a57a178e6ae0fe7fa86e7d81c5233de8560` for special-account derivation;
the Rust executor has no upstream counterpart. The finite matrix does not close
all account statuses, action/output-message paths, due-payment shortfalls,
configuration/seed/library/previous-block variants, tick scheduling or full VM
coverage. Those remain separately tracked parity work.
