# TOS Wallet Send-and-Track Specification

Version: v1.0

## 1. Overview

This document specifies the complete transaction lifecycle for a TOS wallet integration: from fee estimation through transaction submission to on-chain confirmation tracking.

The flow uses the TOS embedded JSON-RPC API exposed by validator-engine. All methods are accessed via `POST /jsonRPC` as standard JSON-RPC 2.0 requests. The OpenAPI definition is published in `doc/openapi.yaml`.

This spec covers the canonical send-and-track path. It does not cover contract deployment, multi-message workflows, or Jetton transfers. Those flows build on the primitives described here.

## 2. Fee Estimation

### Method

`estimateFee`

### Parameters

| Field           | Type   | Required | Description                                          |
|-----------------|--------|----------|------------------------------------------------------|
| `address`       | string | yes      | Sender address (raw, bounceable, or non-bounceable)  |
| `body`          | string | yes      | Base64-encoded BOC of the message body               |
| `init_code`     | string | no       | Base64-encoded BOC of StateInit code (for deploy)    |
| `init_data`     | string | no       | Base64-encoded BOC of StateInit data (for deploy)    |
| `ignore_chksig` | bool   | no       | Skip signature checks during TVM execution (default: true) |

### Response

```json
{
  "ok": true,
  "result": {
    "@type": "query.fees",
    "source_fees": {
      "@type": "fees",
      "in_fwd_fee": 1000000,
      "storage_fee": 100,
      "gas_fee": 3000000,
      "fwd_fee": 1000000
    },
    "destination_fees": []
  }
}
```

### Fee Calculation

Total estimated fee for the sender:

```
total_fee = source_fees.in_fwd_fee
          + source_fees.storage_fee
          + source_fees.gas_fee
          + source_fees.fwd_fee
```

All fee values are in nanotomis (1 tomi = 10^9 nanotomis).

`destination_fees` is an array of fee breakdowns for internal messages generated by the transaction. For a simple transfer from a standard wallet contract, this array is typically empty. Wallets should display the `source_fees` total as the estimated fee.

### Notes

- The estimate executes the message against the current account state. If the account state changes between estimation and submission, the actual fee may differ.
- `ignore_chksig` defaults to true, which means the estimate will succeed even if the message body is unsigned. This is the correct behavior for pre-signing fee display.
- The estimate does not reserve or lock any balance.

## 3. Transaction Submission

### Recommended Method

`sendBocReturnHash`

This is the recommended method for production wallet flows because it returns the message hash needed for tracking.

### Parameters

| Field | Type   | Required | Description                               |
|-------|--------|----------|-------------------------------------------|
| `boc` | string | yes      | Base64-encoded BOC of the external message |

The `boc` must contain a fully constructed and signed external message, including the destination address, the wallet seqno, and the transfer payload.

### Response

```json
{
  "ok": true,
  "result": {
    "status": 1,
    "hash": "base64-encoded-message-hash"
  }
}
```

- `status`: 1 indicates the message was accepted by the node for processing.
- `hash`: Base64-encoded hash of the external message. This is the value used for transaction tracking (see Section 4).

### Alternative Methods

**`sendBoc`** — Accepts the same `boc` parameter but does not return a message hash. The response contains only `status`. Not recommended for tracked flows because there is no reliable way to correlate the submission with the on-chain transaction.

**`sendBocReturnHashNoError`** — Same as `sendBocReturnHash` but never returns a JSON-RPC error. If the liteserver rejects the message, the response still has `ok: true` with `status: -1`. Useful for fire-and-forget scenarios or batch submission where individual errors should not abort the caller.

### Error Handling

If `sendBocReturnHash` returns `ok: false`, the external message was not accepted. Common causes:

- The seqno in the message does not match the wallet's current seqno.
- The message signature is invalid.
- The account balance is insufficient to cover fees.
- The message has already been processed (duplicate submission).

The error response body contains a human-readable `error` string and an integer `code`. See Section 7 for the error classification.

When the node returns an error, the message was not injected into the processing queue. It is safe to construct a new message (with the same seqno, if the original was never processed) and retry.

## 4. Transaction Tracking

After `sendBocReturnHash` returns successfully, the message has been accepted by the node but has not yet been included in a block. The wallet must poll for confirmation.

### Tracking Procedure

1. Call `getTransactions` on the sender's account with `limit` set to a small number (5 is sufficient for most cases).
2. For each transaction in the response, compare the `in_msg_hash` field against the `hash` returned by `sendBocReturnHash`.
3. If a match is found, the transaction is confirmed.
4. If no match is found, wait and retry.

### Polling Strategy

| Parameter          | Recommended Value | Notes                                               |
|--------------------|-------------------|-----------------------------------------------------|
| Poll interval      | 1-2 seconds       | Shorter intervals waste resources; longer delays UX  |
| Timeout            | 30 seconds        | Masterchain block time is ~5 seconds                 |
| Extended timeout   | 60 seconds        | For shardchain transactions under heavy load         |
| Transaction limit  | 5                 | Recent transactions only; the target should be near the top |

If the timeout expires without a match, the wallet should:

1. Check whether the wallet's seqno has incremented (via `getWalletInformation`). If it has, the transaction was processed but the polling window may have been too narrow. Widen the `limit` and retry.
2. If the seqno has not incremented, the message may have expired or been dropped. The wallet may construct and submit a new message with the same seqno.

### The `in_msg_hash` Field

The `in_msg_hash` field is a TOS extension. It is the base64-encoded hash of the inbound message cell for each transaction. For transactions triggered by an external message, this hash matches the hash returned by `sendBocReturnHash`.

This field is present in the response of both `getTransactions` and `getTransactionsStd`.

Standard TON API implementations do not include `in_msg_hash` in the `getTransactions` response. Wallets targeting TOS should use this field for tracking. Wallets targeting both TOS and standard TON may need to fall back to seqno-based detection on non-TOS nodes.

## 5. Transaction Details

### Method

`getTransactions`

### Parameters

| Field     | Type    | Required | Description                                    |
|-----------|---------|----------|------------------------------------------------|
| `address` | string  | yes      | Account address                                |
| `limit`   | integer | no       | Number of transactions to return (default: 10, max: 100) |
| `lt`      | string  | no       | Start from this logical time (must be paired with `hash`) |
| `hash`    | string  | no       | Transaction hash at `lt` (base64 or hex; must be paired with `lt`) |

When `lt` and `hash` are omitted, the response starts from the most recent transaction. When provided, they specify the starting point for pagination.

### Response

The response is a JSON array of transaction objects:

```json
[
  {
    "@type": "raw.transaction",
    "block_id": {
      "@type": "ton.blockIdExt",
      "workchain": -1,
      "shard": "-9223372036854775808",
      "seqno": 12345,
      "root_hash": "...",
      "file_hash": "..."
    },
    "data": "base64-encoded-transaction-BOC",
    "utime": 1714000000,
    "transaction_id": {
      "@type": "internal.transactionId",
      "lt": "12345678",
      "hash": "base64-encoded-hash"
    },
    "fee": "5000000",
    "account": "hex-encoded-256-bit-account-address",
    "in_msg_hash": "base64-encoded-inbound-message-hash"
  }
]
```

### Field Reference

| Field             | Type   | Description                                              |
|-------------------|--------|----------------------------------------------------------|
| `@type`           | string | Always `"raw.transaction"`                                |
| `block_id`        | object | Block that contains this transaction                      |
| `data`            | string | Base64-encoded BOC of the raw transaction cell            |
| `utime`           | integer| Unix timestamp of the block containing this transaction   |
| `transaction_id`  | object | Unique identifier: `lt` (logical time) and `hash`        |
| `fee`             | string | Total fees charged, in nanotomis                          |
| `account`         | string | 256-bit account address in hex                            |
| `in_msg_hash`     | string | Hash of the inbound message that triggered this transaction |

The `data` field contains the full transaction BOC. Clients that need to inspect outbound messages, compute phases, or action phases should deserialize this BOC using a TOS/TON SDK.

The `transaction_id` (`lt` + `hash`) uniquely identifies a transaction on-chain. Use these values for pagination, deduplication, and cross-referencing with block explorers.

### Standardized Variant

`getTransactionsStd` returns the same data wrapped in a `blocks.rawTransactions` envelope with an explicit `previous_transaction_id` field for cursor-based pagination:

```json
{
  "ok": true,
  "result": {
    "@type": "blocks.rawTransactions",
    "transactions": [ ... ],
    "previous_transaction_id": {
      "@type": "internal.transactionId",
      "lt": "12345670",
      "hash": "..."
    }
  }
}
```

## 6. Account State After Transaction

After a transaction is confirmed, the wallet should refresh the account state.

### Methods

**`getWalletInformation`** — Returns wallet-specific fields. Preferred for wallet integrations.

| Response Field          | Type    | Description                                    |
|-------------------------|---------|------------------------------------------------|
| `wallet`                | boolean | Whether the account is a recognized wallet contract |
| `balance`               | string  | Current balance in nanotomis                    |
| `account_state`         | string  | `"active"`, `"uninitialized"`, or `"frozen"`    |
| `last_transaction_id`   | object  | `lt` and `hash` of the most recent transaction  |
| `wallet_type`           | string or null | Wallet type (e.g. `"wallet v4 r2"`) or null |
| `seqno`                 | integer or null | Current wallet seqno, or null if not a wallet |
| `wallet_id`             | integer or null | Wallet subwallet ID                        |

**`getAddressInformation`** — Returns raw account state including `code` and `data` BOCs. Use when you need contract code or storage data, not just balance and seqno.

### Post-Transaction Checks

1. Verify that `seqno` has incremented by 1 from the value used to construct the message.
2. Verify that `balance` reflects the expected deduction (transfer amount + fees).
3. Verify that `last_transaction_id` matches the `transaction_id` of the confirmed transaction.

If `seqno` has not incremented, the transaction has not been processed yet (or was processed in a different way). Do not construct a new message with the next seqno until the current seqno is confirmed.

## 7. Error Classification

### JSON-RPC Error Codes

| Code     | HTTP Analog | Meaning                           | Client Action                          |
|----------|-------------|-----------------------------------|----------------------------------------|
| `-32602` | 422         | Invalid parameters                | Fix the request and retry              |
| `-32603` | 500         | Internal server error             | Retry with exponential backoff         |
| `-32601` | 404         | Method not found                  | Client bug — check method name         |
| `-32000` | 401         | Unauthorized                      | Missing or invalid `X-API-Key` header  |
| `409`    | 409         | Not a token                       | `getTokenData`-specific; not relevant to send flow |

### Error Response Shape

```json
{
  "ok": false,
  "error": "human-readable error message",
  "code": -32602
}
```

### Timeout Handling

If a request receives no response within 30 seconds (the server's default `request_timeout`):

- **For read methods** (`getTransactions`, `getWalletInformation`, etc.): retry the query. Read methods are idempotent.
- **For `sendBocReturnHash`**: do NOT blindly resubmit. First check the wallet's seqno via `getWalletInformation`. If the seqno has incremented, the message may have been processed despite the timeout. If the seqno has not incremented, it is safe to resubmit the same message.

### Liteserver-Level Errors

When the embedded liteserver rejects a query, the server translates the liteserver error into a JSON-RPC error with code `-32603`. The `error` string contains the liteserver's error message. Common liteserver errors during send:

- `"external message not accepted"` — The message was syntactically valid but rejected by the node (wrong seqno, bad signature, insufficient balance, expired).
- `"timeout"` — The liteserver query timed out internally.

## 8. Best Practices

### Message Construction

- Always call `getWalletInformation` to get the current `seqno` before constructing an external message. Never assume the seqno.
- Never resubmit an external message without confirming that the seqno has not been consumed. Resubmitting with an already-used seqno will fail. Submitting with an incremented seqno without confirming the previous transaction will skip a seqno and may lose funds if the original transaction eventually lands.
- Set a reasonable expiration time on external messages (typically 60 seconds). This prevents stale messages from being processed long after the user has abandoned the flow.

### Tracking

- Always use `sendBocReturnHash` instead of `sendBoc` for production wallet flows. Without the returned hash, tracking requires heuristics (balance change detection, seqno change detection) that are unreliable under concurrent transactions.
- Use `in_msg_hash` correlation for tracking. Do not rely on balance-change detection, which fails when multiple transactions land in the same polling interval.
- Start polling immediately after `sendBocReturnHash` returns. Do not wait for a fixed delay before the first poll.

### State Queries

- Cache the `last` block from `getMasterchainInfo` if you need to correlate queries with a specific chain state. The `seqno` from this response can be used with methods that accept a block reference.
- Use `getWalletInformation` for wallet-specific queries (balance, seqno, wallet type). Use `getAddressInformation` only when you need raw contract code or data.

### Reliability

- Implement exponential backoff for `-32603` errors. Start at 1 second, cap at 30 seconds.
- For user-facing flows, show the transaction as "pending" immediately after `sendBocReturnHash` succeeds, then update to "confirmed" once tracking finds the transaction.
- If tracking times out, do not show the transaction as "failed" immediately. Check the seqno first. Network delays or temporary node issues can cause tracking to miss the confirmation window.

## 9. Example Flow

```
# 1. Get current wallet state
wallet = rpc("getWalletInformation", {address: sender})
seqno  = wallet.result.seqno
balance = wallet.result.balance

# 2. Estimate fees
fees = rpc("estimateFee", {
  address: sender,
  body: base64_encode(message_body_boc)
})
total_fee = fees.result.source_fees.in_fwd_fee
          + fees.result.source_fees.storage_fee
          + fees.result.source_fees.gas_fee
          + fees.result.source_fees.fwd_fee

# 3. Verify sufficient balance
assert balance >= amount + total_fee

# 4. Construct and sign the external message
msg = construct_external_message(
  sender_key  = private_key,
  seqno       = seqno,
  destination = recipient,
  amount      = amount,
  expire_at   = now() + 60
)

# 5. Submit
result = rpc("sendBocReturnHash", {boc: base64_encode(serialize(msg))})
msg_hash = result.result.hash

# 6. Track confirmation
start = now()
while now() - start < 30:
  txs = rpc("getTransactions", {address: sender, limit: 5})
  for tx in txs.result:
    if tx.in_msg_hash == msg_hash:
      # Transaction confirmed
      confirmed_tx = tx
      break
  if confirmed_tx:
    break
  sleep(1.5)

if not confirmed_tx:
  # Timeout — check seqno
  wallet2 = rpc("getWalletInformation", {address: sender})
  if wallet2.result.seqno > seqno:
    # Seqno advanced — transaction likely processed, widen search
    txs = rpc("getTransactions", {address: sender, limit: 20})
    for tx in txs.result:
      if tx.in_msg_hash == msg_hash:
        confirmed_tx = tx
        break
  if not confirmed_tx:
    # Transaction not found — may retry with same seqno
    report_timeout()

# 7. Verify final state
wallet_final = rpc("getWalletInformation", {address: sender})
assert wallet_final.result.seqno == seqno + 1
```

## 10. Stability Level

This send-and-track flow is **Level 2 (Supported Surface)** per `tos-standards-map.md`.

### What This Means

- Method names (`estimateFee`, `sendBocReturnHash`, `getTransactions`, `getWalletInformation`) are stable and will not be renamed or removed without a documented deprecation period.
- Response field names and types described in this document are stable.
- The `in_msg_hash` field in `getTransactions` responses is a TOS extension not present in the standard TON HTTP API. Clients building for TOS can rely on it. Clients building for cross-network compatibility should implement a fallback tracking strategy.
- Error codes and their meanings are stable.

### Path to Level 1

This flow will be promoted to Level 1 (Canonical Standard) when:

- The Q2 exit criteria are met: "a wallet integrator can support the canonical send-and-track flow from one main API surface."
- At least one production wallet integration has been completed using this spec.
- The `in_msg_hash` tracking mechanism has been validated under production load.
