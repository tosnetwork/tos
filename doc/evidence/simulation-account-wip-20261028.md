The eventual one-shot entry point must first authenticate/freshness-check the target through the existing anchor/live path, obtain complete configuration at that target, call the proof-bound preparation path and then enforce basechain/fixed-self-pay-code/supported-VM/message/StateInit policy. ## Author self-check

- Callers: searched both new declarations/definitions and CMake/CI wiring. Current callers are the native tests; production simulation integration is still pending. Existing public verifier, phone ABI and read-only account APIs are unchanged. `restore_simulation_account` accepts already authenticated native observations, not endpoint JSON; its direct synthetic test calls do not establish proof capabilities. `prepare_simulation_account` is the proof-bound wrapper the future adapter must use.
- Binding/order: require the configuration's block id to equal the authenticated target; bound the account TL reply before copying it; require its reference id to match; preflight Account and both proof BOCs before cell allocation; validate the shard/account proof through the existing AccountState validator; scan the actual complete account representations; wrap the exact Account cell with the proven ShardAccount last transaction hash/start LT; call the native Account unpacker, then derive context using its real storage end LT. The result is an execution input, never a future VerifiedRead or a replacement for an authenticated account cache entry.
- State fidelity: native unpacking preserves storage usage/hash, last_paid, due_payment, balance/extra currencies, original Account, active/uninitialized/frozen status and code/data/library references. No balance-only state is synthesized for existing accounts. Only a null proven account root with zero transaction history/hash can use native init_new. A present account_none cell is refused rather than silently converted to dictionary absence. Native block LT is assigned explicitly; time uses shard/masterchain/local floors and the checked context helper. AccountStorage end LT is distinct from the ShardAccount start LT.
- Frozen state is restored for fidelity, not accepted for payment: the eventual message adapter still needs the exact supported StateInit/data and real signatures before it may simulate restoration/execution. The component does not invent missing code or clear counters. The same distinction applies to uninitialized/deleted account support and future backup/recovery policy.
- Current prototype scope: the recorded real fixture is a masterchain Elector account on the old VM18 development network. It validates generic native restoration and exact proof/metadata binding, including the existing special-account flag. It is not a fresh basechain self-pay proof, phone-signed deployment/payment or production-network test. Final public execution remains planned for fixed self-pay/basechain policy. New absent accounts follow the existing native initialization semantics; no special exemption is invented.
