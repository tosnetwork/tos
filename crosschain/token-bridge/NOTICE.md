## Reviewed deltas against the pinned upstream

Everything below is a deliberate change; anything else appearing in a diff against the pinned commits is unreviewed and must be investigated. There are seventeen deltas.

1. Renames to TOS semantics: identifiers, file names, and comments. Assembler mnemonic strings `STGRAMS`→`STTOMIS` and `LDGRAMS`→`LDTOMIS` resolve to the same opcodes (`0xFA02`, `0xFA00`) in the TOS assembler.
2. `stdlib.fc`: removed a duplicate `load_coins`/`store_coins` declaration pair that the mnemonic rename collapsed onto the existing one.
3. `jetton-minter.fc`: the wrapped-token metadata URI prefix is now `https://bridge.tos.network/token/`. This literal is compiled into the minter code, so **the minter code hash and every state-init-derived minter address differ from the upstream artifacts by design**. Deployment tooling must derive addresses from this build, never from upstream expectations.
4. Removed operator entry points that embedded upstream deployed addresses or oracle sets: `scripts/deploy-mainnet-bridge.ts` and `scripts/call-unlock.ts` (with its `tonweb` dependency). `scripts/deploy-bridge.ts` and `scripts/call-lock.ts` now read every deployment-specific value from the environment.
5. `Bridge.sol`: governance votes are now bound to live state. A rotation must name the set it replaces (`oracleSetHash == keccak256(abi.encode(oracleSet))`), and lock-status and per-token disable nonces must strictly increase. Upstream checked only `finishedVotings`, which stops a digest that already executed but leaves a signed-but-unexecuted vote valid forever — so a stale rotation could undo a newer one whenever the two sets overlap enough to keep meeting quorum. The signed payloads already carried these values, so the signing format is unchanged.
6. `jetton-bridge.fc`: a swap vote carries no forward amount. Upstream let the vote ask the receiving wallet to forward coins to the recipient, an action the wallet could fail on in the middle of a mint that spans three transactions. Mints never forward here.
7. `Bridge.sol`: the constructor takes the initially disabled tokens as a parameter instead of compiling in the upstream deployment's wrapped-coin addresses, which named contracts this repository does not control. Deployments must name their own coin-plane wrapped token.
8. **New network semantics, not a rename.** The pinned upstream ships one configuration slot (`build-config79.fif`, Ethereum). `tvm/params/bsc.fc`, `tvm/params/polygon.fc` and `tvm/params/tron.fc` — ConfigParams 81, 82 and 83 — are added here. Slot 83 and its Tron chain id have no upstream counterpart at all: the schema entry in `crypto/block/block.tlb` is new, and no counterparty contract has ever run on Tron. `tronbox.js` and `migrations-tron/` build the same Solidity plane with `tron-solc`, and `test-tron/` executes it inside Tron's virtual machine on a throwaway local node. Deployment to a public Tron network, and the chain id of that network specifically, remain unverified. They follow the upstream parameter shape, but no upstream artifact covers them, so they carry no upstream deployment history and must be reviewed as new configuration.
9. `tvm/contracts/multisig.fc`: the signed query body now carries the network's 32-bit signed global id immediately after `wallet_id`, compared against ConfigParam 19 via the `GLOBALID` instruction (exit code 44 on mismatch). Upstream's query separated deployments (`wallet_id`) but not networks, so two networks bootstrapped from one StateInit with a key-sharing oracle set accepted each other's queries verbatim. This signed-payload change must be adopted atomically by every query builder. `tvm/tests/replay-wrong-global-id.js` executes the compiled contract and proves a query naming another network is refused before any dispatch or state change.
10. `tvm/contracts/multisig.fc`: an oracle key anyone can sign for is refused with exit code 45. That is every Ed25519 8-torsion encoding the verifier accepts -- the eight canonical ones, the identity and the order-2 point with the sign bit set, and every non-canonical y -- as listed by `strong-ed25519-key.fc`, a byte-identical copy of `crypto/smartcont/strong-ed25519-key.fc` that `scripts/verify-token-bridge.py` keeps in sync. Upstream verified a stored key against whatever signature came with it, so an owner set holding such a key gave anyone a forged root signature or co-signature. `create_init_state` refuses an owner set containing one, and a stored one (a hand-built StateInit) is refused before its signature is checked, as root, as co-signer and in `check_query_signatures`. `tvm/tests/weak-owner-key.js` forges root and co-signatures under both sign-bit aliases and shows they are refused while two real oracles still execute.
11. `tvm/contracts/jetton-wallet.fc`: a burn naming the zero address as its counterparty destination is refused with `error::zero_destination` (397) while the holder still has the tokens. The ERC-20 release to that address reverts, and by then the jettons on this side would already be destroyed. The token-bridge sandbox covers it (`t_x8_votes_outside_the_namespace_and_burns_to_nowhere_are_refused`).
12. **Settlement protocol** (`SETTLEMENT-PROTOCOL.md`; `tvm/contracts/settlement.fc`, new). Upstream counted supply when the minter dispatched a credit, ignored bounces and sent the burn notification non-bounceable, so a failure in either three-transaction path inflated supply or burned tokens with no log. The bridge, the minter and the wallets now keep durable records under identities bound to canonical descriptors, number their operations densely on four channels with acknowledged windows, decide every operation once and let anyone fund the retransmission of an unfinished one from its record alone. Every leg prices its step and the rest of its path at current prices and spends only its incoming value. `SECURITY.md` ("Completion of mints and burns") summarises the protocol, its owner-approved stranding scope and what remains; `tosctl/src/node-control/contracts/tests/token_bridge_sandbox.rs` executes the test matrix and every transaction is replayed in the native engine.
13. **Source generations and lock nonces** (`Bridge.sol`, `SignatureChecker.sol`). Every EVM lock gets a dense nonce and a record, under a source generation that an oracle vote binds to one TOS bridge address and life. The TOS bridge pins one EVM chain id and EVM bridge address, accepts business only after a generation naming it is activated, and identifies a swap by `(chain id, EVM bridge, generation, nonce)` instead of `cell_hash(ext_chain_hash, internal_index)`. `cancel_lock` makes a lock terminally cancelled on TOS, after which `refundLock` returns it on the EVM side once. The `Lock` event and the swap vote change accordingly; `tests/vectors/source-events.json` holds the fields both sides check.
14. **Opcodes.** The settlement opcodes are numbered from 40 (`settlement.fc`); the previous completion opcodes 21 to 27 do not exist and are refused like any unknown opcode. New error codes 375 to 388 and new log topics `LOG_SWAP_CANCELLED`, `LOG_LIABILITY_STRANDED`, `LOG_CHANNEL_TERMINAL` and `LOG_GENERATION_ACTIVATED` are defined in `settlement.fc`. `errors.fc` adds three more, each documented where it is defined: `error::supply_bound` (389), a wallet balance above `2^120 - 1`; `error::swap_not_paid` (396), a swap vote for a lock nobody paid for; and `error::zero_destination` (397, item 11). Codes 390, 391 and 393 to 395 were declared for an earlier completion design and 398 for a swap forward amount the vote no longer carries (item 6); nothing threw them, and they are removed and left unassigned.
15. **Storage layouts.** The bridge, minter and wallet storage are those of `SETTLEMENT-PROTOCOL.md` section 5, with the differences listed there. The minter's initial data includes its bridge, so every minter and wallet address differs from upstream. Upstream's getters for the old layouts are gone; the settlement getters (`get_bridge_state`, `get_swap`, `get_channel`, `get_mint`, `get_holder`, `get_settlement_state`, `get_advance_cost` and others) are new.
16. `tvm/contracts/new-bridge.fif` takes the EVM chain id and EVM bridge address and builds the storage of item 15; it includes `jetton-bridge.fif`, the name `scripts/build-token-bridge.sh` produces. `token_bridge_sandbox` runs the script and takes the bridge it creates through a complete mint and burn.
17. **The oracle multisig may only vote.** `tvm/contracts/multisig.fc` appends `allowed: HashmapE 256 ()`, the masterchain account ids of the bridges its queries may reach, to its data, after `lock_until`; the StateInit, and so the address, commits to it, and nothing ever changes it. The multisig never reads ConfigParam. `check_proposed_query`, the single place a query's message is inspected (a pending query is approved only with a byte-identical copy, exit code 36), refuses anything but a vote: a destination that is not an allowlisted masterchain address (46), a message that is not internal and bounceable (47), a send mode outside 0 to 3 (48), a value above `MAX_VOTE_VALUE` (10 TOS) or with extra currencies (49), and a StateInit (50). `create_init_state(wallet_id, n, k, owners, allowed)` refuses an empty allowlist (51), `get_allowed_bridges` returns it, and `new-multisig.fif` takes the bridge addresses as its trailing arguments and refuses none, a non-masterchain one or a repeated one. The pinned upstream multisig lets a quorum send any message: its "multisig & config v3" revision removed the earlier rule that the multisig may send only bounceable messages to the bridge ConfigParam names, and the `lock_until` check, so that the coin-bridge multisig could pay out swept rewards itself with non-bounceable transfers. That rule had also failed open: with the parameter missing, the multisig was unrestricted. The oracle flows need only bounceable votes to a bridge: the swap, `cancel_lock`, `activate_generation`, `get_reward` and `change_collector` votes, authenticated as `is_oracles` by `token-bridge.fc`. The allowlist is explicit, not "the bridge ConfigParam names", because a replaced bridge still completes its old generation's locks (`SETTLEMENT-PROTOCOL.md` section 4, "A replaced bridge") while the configuration names its successor. `lock_until`, upstream's launch time-lock, stays in the layout, is always 0 from `create_init_state` and the script, and is inert: nothing reads it, and activation is already gated by the validators' ConfigParam vote naming this multisig. `tosctl/src/node-control/contracts/tests/bridge_multisig_sandbox.rs` has one test per guard, which `scripts/token-bridge-mutations.py` (controls S01 to S05) shows each guard alone holding, and `token_bridge_sandbox` (`token_bridge/oracles.rs`) votes a `cancel_lock` through a real multisig to a replaced bridge, every transaction replayed in the native engine.

The relayer's protocol description (`docs/protocol.md` in the separate relayer repository) predates items 9, 13 and 17 and is stale on three points, to be brought in line as part of the relayer work (T11):

- it delivers multisig queries as external messages, but the multisig takes queries only by internal message (`recv_external` only initializes it);
- its query layout has no `global_id`, the signed 32-bit network id that follows `wallet_id` (item 9);
- its swap vote is the upstream body, not the body of item 13: `generation:uint32 n:uint64 evm_chain_id:uint32 evm_bridge:uint160 recipient:uint256 amount:Coins ^wrapped_token_data`.

Historical upstream network BOCs, deployed addresses, oracle key sets, and mainnet deployment commands are intentionally excluded and must not be reused for TOS.
