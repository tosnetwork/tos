## Reviewed deltas against the pinned upstream

Everything below is a deliberate change; anything else appearing in a diff against the pinned commits is unreviewed and must be investigated.

1. Renames to TOS semantics: identifiers, file names, and comments. Assembler mnemonic strings `STGRAMS`→`STTOMIS` and `LDGRAMS`→`LDTOMIS` resolve to the same opcodes (`0xFA02`, `0xFA00`) in the TOS assembler.
2. `stdlib.fc`: removed a duplicate `load_coins`/`store_coins` declaration pair that the mnemonic rename collapsed onto the existing one.
3. `jetton-minter.fc`: the wrapped-token metadata URI prefix is now `https://bridge.tos.network/token/`. This literal is compiled into the minter code, so **the minter code hash and every state-init-derived minter address differ from the upstream artifacts by design**. Deployment tooling must derive addresses from this build, never from upstream expectations.
4. Removed operator entry points that embedded upstream deployed addresses or oracle sets: `scripts/deploy-mainnet-bridge.ts` and `scripts/call-unlock.ts` (with its `tonweb` dependency). `scripts/deploy-bridge.ts` and `scripts/call-lock.ts` now read every deployment-specific value from the environment.
5. `Bridge.sol`: governance votes are now bound to live state. A rotation must name the set it replaces (`oracleSetHash == keccak256(abi.encode(oracleSet))`), and lock-status and per-token disable nonces must strictly increase. Upstream checked only `finishedVotings`, which stops a digest that already executed but leaves a signed-but-unexecuted vote valid forever — so a stale rotation could undo a newer one whenever the two sets overlap enough to keep meeting quorum. The signed payloads already carried these values, so the signing format is unchanged.
6. `jetton-bridge.fc`: a swap whose `forward_coins_amount` is non-zero is rejected outright (`error::forward_amount_not_zero`, a new code 398). Upstream only required `bridge_mint_fee > forward_coins_amount`. A non-zero forward amount is the sole action the receiving wallet can fail on, and the mint spans three transactions with no atomicity, so such a failure inflates supply with no wallet credit and no way to reconcile.
7. `Bridge.sol`: the constructor takes the initially disabled tokens as a parameter instead of compiling in the upstream deployment's wrapped-coin addresses, which named contracts this repository does not control. Deployments must name their own coin-plane wrapped token.
8. **New network semantics, not a rename.** The pinned upstream ships one configuration slot (`build-config79.fif`, Ethereum). `tvm/params/bsc.fc`, `tvm/params/polygon.fc` and `tvm/params/tron.fc` — ConfigParams 81, 82 and 83 — are added here. Slot 83 and its Tron chain id have no upstream counterpart at all: the schema entry in `crypto/block/block.tlb` is new, and no counterparty contract has ever run on Tron. `tronbox.js` and `migrations-tron/` build the same Solidity plane with `tron-solc`, and `test-tron/` executes it inside Tron's virtual machine on a throwaway local node. Deployment to a public Tron network, and the chain id of that network specifically, remain unverified. They follow the upstream parameter shape, but no upstream artifact covers them, so they carry no upstream deployment history and must be reviewed as new configuration.
9. `tvm/contracts/multisig.fc`: the signed query body now carries the network's 32-bit signed global id immediately after `wallet_id`, compared against ConfigParam 19 via the `GLOBALID` instruction (exit code 44 on mismatch). Upstream's query separated deployments (`wallet_id`) but not networks, so two networks bootstrapped from one StateInit with a key-sharing oracle set accepted each other's queries verbatim. This signed-payload change must be adopted atomically by every query builder. `tvm/tests/replay-wrong-global-id.js` executes the compiled contract and proves a query naming another network is refused before any dispatch or state change.
10. `tvm/contracts/multisig.fc`: an oracle key anyone can sign for is refused with exit code 45. That is every Ed25519 8-torsion encoding the verifier accepts -- the eight canonical ones, the identity and the order-2 point with the sign bit set, and every non-canonical y -- as listed by `strong-ed25519-key.fc`, a byte-identical copy of `crypto/smartcont/strong-ed25519-key.fc` that `scripts/verify-token-bridge.py` keeps in sync. Upstream verified a stored key against whatever signature came with it, so an owner set holding such a key gave anyone a forged root signature or co-signature. `create_init_state` refuses an owner set containing one, and a stored one (a hand-built StateInit) is refused before its signature is checked, as root, as co-signer and in `check_query_signatures`. `tvm/tests/weak-owner-key.js` forges root and co-signatures under both sign-bit aliases and shows they are refused while two real oracles still execute.
11. `tvm/contracts/jetton-wallet.fc`: a burn naming the zero address as its counterparty destination is refused with `error::zero_destination` (397) before the balance is reduced. The ERC-20 release to that address reverts, and by then the jettons on this side would already be destroyed. `tvm/tests/zero-destination.js` covers it.
12. `tvm/contracts/jetton-bridge.fc`: a swap vote executes only against a paid swap. `pay_swap` records its payment under a key the contract derives from the source event (`cell_hash(ext_chain_hash, internal_index)`) rather than taking one from the payer, and the vote spends that key or is refused with `error::swap_not_paid` (396), so the oracle multisig never mints out of the bridge's own balance and one fee pays for one mint. The set is held in a new `paid_swaps:(HashmapE 256 Unit)` storage field. `tvm/tests/unpaid-swap.js` covers it.
13. **Mint and burn completion protocol** (`tvm/contracts/settlement.fc`, new). Upstream counted supply when the minter dispatched a credit, ignored bounces, and sent the burn notification to the bridge non-bounceable, so a failure in either three-transaction path inflated supply or burned tokens with no log. Each step now reports back: the wallet confirms a credit, the minter counts supply only on that confirmation and reports `mint_completed`/`mint_failed` to the bridge, the bridge answers a logged burn with `burn_recorded`, a bounced burn notification is credited back to its owner, and a failed mint or refund stays recorded and can be retried by anyone. Every step's gas and forwarding cost is priced in the contract and a step that cannot fund the rest of its path is refused. `SECURITY.md` ("Completion of mints and burns") describes the protocol and its remaining limits; `tosctl/src/node-control/contracts/tests/token_bridge_sandbox.rs` executes it with real action and bounce phases and every transaction is replayed in the native engine.
14. New opcodes, all defined in `settlement.fc`: `mint_credited` (22, wallet to minter), `mint_completed` (23, minter to bridge), `mint_failed` (24, minter to bridge), `retry_mint` (25, anyone to bridge), `burn_recorded` (26, bridge to minter) and `retry_refund` (27, anyone to minter). New error codes 389-395 in `errors.fc`, and new log topics `LOG_MINT_FAILED` and `LOG_BURN_REFUND_FAILED`.
15. **Bridge storage layout.** `jetton-bridge.fc` storage is now `collector_address jetton_minter_code:^Cell jetton_wallet_code:^Cell paid_swaps:(HashmapE 256 Unit) next_mint_id:uint64 pending_mints:(HashmapE 64 PendingMint)`. Upstream stored only the first three fields. `get_pending_mint` and `get_next_mint_id` are new getters.
16. **Minter storage layout.** `jetton-minter.fc` storage is now `total_supply:Coins in_flight:Coins content:^Cell jetton_wallet_code:^Cell next_burn_id:uint64 pending_burns:(HashmapE 64 PendingBurn)`. Upstream stored `total_supply`, `content` and the wallet code. Because the bridge builds the minter's initial data, this also changes every minter address. `get_pending_burn`, `get_next_burn_id`, `get_in_flight` and the cost getters are new.
17. `tvm/contracts/jetton-wallet.fc`: a new branch for a credit sent by the wallet's own minter (a mint or a refunded burn). It requires a zero forward amount, keeps the storage reserve, and answers with `mint_credited` as its only action, sent so that a failure to send it bounces the credit back to the minter. Transfers between wallets take the unchanged upstream path.
18. `tvm/contracts/new-bridge.fif` builds the storage of item 15 and includes `jetton-bridge.fif`, the name `scripts/build-token-bridge.sh` produces; upstream included `bridge_code2.fif`, which nothing here builds. `token_bridge_sandbox` runs the script and takes the bridge it creates through a complete mint, so a storage layout the script and the contract disagree on fails the suite.

Historical upstream network BOCs, deployed addresses, oracle key sets, and mainnet deployment commands are intentionally excluded and must not be reused for TOS.
