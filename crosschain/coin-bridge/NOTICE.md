## Reviewed deltas against the pinned upstream

Everything below is a deliberate change; anything else appearing in a diff against the pinned commits is unreviewed and must be investigated.

1. Renames to TOS semantics: identifiers, file names, and comments. Assembler mnemonic strings `STGRAMS`→`STTOMIS` and `LDGRAMS`→`LDTOMIS` resolve to the same opcodes (`0xFA02`, `0xFA00`) in the TOS assembler.
2. `Bridge.sol`: all oracle-set validation moved into `updateOracleSet`, so construction and rotation share it. Upstream validated only on rotation and only for duplicates, so a one- or two-member deployment started with a threshold of zero or one, and the zero address — the value `ecrecover` returns on failure — could be installed as a member. The set must now hold at least three distinct non-zero members on every path.
3. `Bridge.sol`: the vote threshold changed from `floor(2n/3)` to `(2n + 2) / 3`. The floor form is satisfied by half the set at sizes that are not multiples of three: four members needed only two signatures. The ceiling form is what the same upstream project adopted in its later token-bridge generation; thresholds are unchanged at multiples of three.
4. `migrations/` and the test suites deploy a three-member development set accordingly, the test utilities gained a `sortedSignatures` helper so multi-signature votes satisfy the strict signer ordering rule, and a threshold matrix test asserts the expected signature count at set sizes three through eight.
5. The test harness normalizes `eth_sign` recovery values, which upstream assumed to be `0`/`1`, across dev-chain generations.
6. `Bridge.sol`: oracle-set hashes and burn-status nonces must strictly increase. Upstream checked only `finishedVotings`, so a signed-but-unexecuted governance vote stayed valid forever and a stale one could undo a newer one. This makes the nonce an ordered sequence rather than an arbitrary unique label, which the oracle daemon must honour.
7. Named-network entries were removed from both `migrations/` and `truffle-config.js`, along with the publicly known development mnemonic they carried and the now-unused wallet provider dependency. An endpoint plus a signing key plus an oracle set is a deployment decision that belongs in a reviewed manifest.
8. `evm/contracts/SignatureChecker.sol`: all three EVM vote digests now add EIP-1344 chain-ID domain separation in the exact order `magic, address(this), chainId, fields`. The Solidity 0.7.x contract reads `chainid()` through inline assembly; the test signer takes the chain ID explicitly. This signed-payload change is intentionally not byte-identical to the pinned upstream and must be adopted atomically by every oracle signer. `evm/test/vectors/chain-id-domain-separation.json` pins the cross-implementation wire values, while the dual-Ganache test proves that mint, oracle-set, burn-status, and legacy-format signatures cannot replay into another chain-ID domain at the same contract address.
9. `tvm/{ethereum,bsc}/multisig-code.fc`: the signed query body now carries the network's 32-bit signed global id immediately after `wallet_id`, compared against ConfigParam 19 via the `GLOBALID` instruction (exit code 44 on mismatch). Upstream's query separated deployments (`wallet_id`) but not networks, so two networks bootstrapped from one StateInit with a key-sharing oracle set accepted each other's queries verbatim. This signed-payload change must be adopted atomically by every query builder. `tvm/tests/replay-wrong-global-id.js` executes the compiled contract and proves a query naming another network is refused before any dispatch or state change.

10. `tvm/{ethereum,bsc}/bridge_code.fc`: the migrate vote (operation 4) is now a closed loop. Upstream sent `total_locked` to the configured bridge address with body opcode `0xf00d` but had no receiving branch and never updated the sender's counter, so the migrated coins landed on the new bridge as plain balance — sweepable by a reward vote — while its `total_locked` stayed zero (bricking releases) and the old bridge still claimed to back funds it no longer held. The sender now zeroes `total_locked` after composing the transfer, `recv_internal` gained an `0xf00d` branch that credits `total_locked` by the attached value (safe from any sender: balance and counter rise equally), and the formerly ignored bounce path re-credits a returned `0xf00d` transfer so a rejected migration leaves the funds locked. `tvm/tests/migrate.js` executes the full cycle, including the bounce and a reward sweep that must not touch the migrated funds; the shared test harness gained an opt-in bounced-message header for this.
11. `tvm/{ethereum,bsc}/bridge_code.fc`: `store_fees` now rejects a network fee below 110000000 (exit code 392). Upstream accepted an all-zero fee schedule while every accepted swap pays a fixed 0.1 receipt from the bridge balance, so a zero-fee vote made each swap reduce the balance backing `total_locked`. The floor (receipt cost plus headroom) makes such a configuration unrepresentable; `tvm/tests/change-fee-floor.js` proves rejection below the floor and acceptance at it.
12. Zero-destination swaps are refused in both directions. `create_swap_from_tos` throws exit code 307 on a zero external destination (upstream minted wrapped coins to the zero address, burning them while the native coins stayed locked), covered by `tvm/tests/tos2eth-zero-destination.js` on both entry points. `WrappedTOS.sol` `burn`/`burnFrom` now require a non-zero TOS address hash and an amount in `(0, 2^64)` — the range the TVM release path reads — so a burn that could never be released is rejected instead of destroying wrapped coins.

Historical upstream network BOCs, prebuilt compile outputs, deployed addresses, oracle key sets, and mainnet deployment command files are intentionally excluded and must not be reused for TOS.
