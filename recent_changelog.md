## 2026.11-1 Update

Tagged `v2026.11-1`. It follows `v2026.11` and changes how a release is built, published and verified, and which hosts may validate. It changes no consensus rule, price or configuration value.

1. `tosctl` is part of the release: `tosctl-linux-x86_64` and `tosctl-linux-arm64`, built by the node recipe from the tagged commit with the pinned Rust toolchain and the committed `Cargo.lock`, for a fixed CPU baseline, and listed in the same build record as the node binaries. A host that installs from a release needs no Rust toolchain. `tosctl` needs `libssl.so.3` and `libcrypto.so.3` (Ubuntu package `libssl3t64`).
2. Every published file is attested. The publisher signs build provenance, through Sigstore, for every file `SHA256SUMS` lists, with the identity of the publishing workflow on `main`; publication waits for it. `release-provenance.json`, itself attested, now records under `assets` the SHA-256 of every other published file, so the one attested record binds each asset to the tag. Verify with `gh attestation verify release-provenance.json --repo tosnetwork/tos --cert-identity https://github.com/tosnetwork/tos/.github/workflows/create-release.yml@refs/heads/main --source-ref refs/heads/main`, then compare the tag, the commit and the asset digests in it. This is the first release with attestations; the identity string above is the expected one and is confirmed against this release after publication. `v2026.11` has none. See `doc/tos-release-policy.md`, "Attestations".
3. Hardware SHA-256 for the SLH-DSA check on arm64. Linux arm64 builds use the ARMv8 SHA2 instructions when the CPU exposes the AES, PMULL, SHA1 and SHA2 extensions and the portable backend otherwise; the transform is the unmodified file of the project the x86-64 SHA-NI transform already comes from, at the same revision. Results are identical on every backend.
4. Validators are permitted by capability, on either architecture: a validator must verify with the hardware SHA-256 backend, on x86-64 (SHA-NI, SSSE3, SSE4.1, SSE4.2) or on arm64 (AES, PMULL, SHA1, SHA2). The portable backend is not allowed for a validator. This replaces item 16 of the 2026.11 update, which allowed x86-64 only. The arm64 figures behind it come from one CPU generation on a shared cloud VM; `doc/Validator.md`, "CPU instruction set", has the measurements, their limits and the deployment receipt a validator keeps, including a time bound for a host that was not measured. The arm64 binaries of `v2026.11` have no hardware backend and must not be used for a validator.
5. The node build of a release refuses to finish unless the hardware SHA-256 backend of its architecture is built in, and its build record names both backend switches (`slhdsa_sha256`).
6. The input an attacker can choose to make the SLH-DSA check most expensive (3,174 SHA-256 compressions, against 2,214 for an honest signature) is a committed test vector, held to exactly that work by a counted check, and timed on x86-64 and arm64 by the pull-request checks.
7. Publisher fixes found by the first release: the collection directory no longer collides with a directory of the repository; a published release is deleted only if its tag moved, since deleting an immutable release would make the tag unusable; the release listing is read again before a step refuses; the publisher refuses a run dispatched from another ref than `main`.
