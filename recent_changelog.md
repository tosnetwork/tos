## 2026.11 Update

The first published release of the TOS node software, tagged `v2026.11`. It includes the 2026.10 update (see `Changelog.md`), which was never published as a release, except where items 2, 3, 8 and 10 here replace it, and the changes made since. It is also the first release whose node binaries are built with the production node recipe, so a node can be installed from the release instead of being built on each host.

1. Release binaries: validator-engine, validator-engine-console, lite-client, generate-random-id, tos-pq-consensus-key, dht-server, tos-rpc and tos-wallet-index are published as plain Linux binaries for x86-64 and arm64, built with the production node recipe (jemalloc for the node and service binaries, a fixed CPU baseline of x86-64-v2 and armv8-a), with a build record, `SHA256SUMS` and `release-provenance.json` together binding every file to the build of the tagged commit. The AppImage archives remain the tool builds and are not the supported way to install a node. See `doc/tos-release-policy.md`.
2. Staking follows the upstream Elector design with ML-DSA-44 keys and signatures: a member is named by the account that sends its stake, an operator wallet or a nominator pool. The validator controller, the stake relay, operating authorizations, ConfigParam 47, `tos-pq-controller` and `tosctl controller` are removed. This replaces the controller-based election path described in the 2026.10 update.
3. Global version 16 enables every execution feature of the binaries: the Falcon-512 signature check, the LMS fee-hash check and the c7 import statistics no longer wait for versions 17 to 19, and 16 is the highest version the binaries support.
4. Consensus: validators record each consensus decision in an own-decision log before signing it, on every network; the `--signing-decision-log` option is gone. This prevents signing twice in a session after the consensus journal is lost, or the database is restored from a file copy or moved to another host. It does not protect against an in-place filesystem or virtual-machine snapshot rollback: never roll a validator back that way, or delete its signing ledger before starting it again. A validator whose earlier signing is unknown (a fresh install of an existing identity, a restore, or a node upgrading to this release) does not sign until three catchain rotations after its first fence block. Every genesis validator of a new chain must run `tos-pq-consensus-key init-signing-ledger --genesis-ceremony` before the node's first start, only for an identity that has never signed; without it the chain does not start. Do not restart a validator-elect within about 15 minutes of its taking office. After a downgrade, remove all signing-ledger directories before upgrading again. See `doc/signing-decision-log.md`. Each consensus key file is held under an exclusive lock. Simplex recovers skip timeouts and vote refusals across a finalization backlog, keeps a late candidate for a finalized slot, and bounds its candidate payload cache in bytes.
5. Networking and admission aligned with the upstream v2026.10 release: QUIC connection handling, Plumtree and overlay broadcasts, ADNL, and external-message admission with priority lanes, a configurable pool and ordered expiry. TOS-only limits on the external message pool, overlay broadcast receive and liteserver admission are removed in favour of the upstream ones.
6. Fees and genesis configuration: masterchain gas and forwarding prices at one twentieth of their earlier values; basechain external gas credit of 20,000; ML-DSA-44 verification priced like the Ed25519 check; SLH-DSA suite 3 verification at 4,500 gas, one attempt per execution; mainnet-scale basechain split parameters; a six-hour initial validator set with the first election inside it; blackhole, complaint and storage prices and the bootstrap amount set for the current genesis.
7. Token naming: "Jetton" is replaced by "Token" across contracts, tools, SDKs and documents. This is a breaking rename for anything that used the old names.
8. Wallets: the self-pay Quantum wallet, which pays its own fees and needs no fee vault, with a successor possession proof; wallet V4 and V5 commit the consumed seqno before executing the signed operation; wallet V5 refuses weak keys, unsendable modes and requests that would exceed the state-size limit; multisig refuses orders that cannot fit the basechain gas limit; `tosctl` requires an explicit wallet version and deploys user contracts to the basechain by default. For the Quantum wallet, independent review, live-network acceptance and activation as the deployed default remain open (`doc/wallet-quantum-release-status.md`).
9. Wallet services: wallet indexing and public JSON-RPC move out of the validator process into `tos-wallet-index` and `tos-rpc`, with verified index snapshots and resumable replay. A validator serves its JSON-RPC without the wallet index. JSON-RPC has one error contract with a strict envelope and parameter checks, and bounded post-quantum explorer evidence interfaces.
10. Shielded pool: the completed second phase-2 ceremony is published with independent verification; a further ceremony is open for registration, and the parameters a deployment will use are not fixed by this release. `tosctl shield` (experimental; exercised only on an isolated local network with an offline Tor stand-in) covers client state, deposits, withdrawals and sends relayed through a bonded relayer over Tor; direct sends are for isolated local networks and tests only. The fixed withdrawal fee is 0.001 TOS for newly generated pools. A native bridge serves mobile wallets. The pool remains **not approved for activation** until the acceptance gates of `artifacts/shielded-pool/PROFILE.md` section 19 pass.
11. Contracts and agent tooling: Treasury Vault V1 contract code with mandatory guardian approval and delayed governance (an implementation proposal, not approved for deployment with real funds); Service Actor settlement that is caller-funded, protects the refund principal and accepts ML-DSA-44 attestors; Native Registry and Agent Account controllers on ML-DSA-44, with `tosctl` builders and signing; Action Authority messages; fixes for the smart-contract audit findings. Removed: the liquid-staking suite with `tosctl pool liquid`, the third-party reference contracts and the stablecoin escrow.
12. Bonded relayer (BR1), an implementation candidate not approved for production activation, for relayed shielded withdrawals: bond actor, quote authentication with ML-DSA-44, bounded quote submission, durable relay core and a Tor onion transport. The provider is local-only by default; a public-testnet pilot needs an explicit build and runtime scope.
13. Operators: verified node data recovery and node data sync, with validator recovery refused through generic snapshot imports; state import bounded against disk exhaustion; archive readers that write nothing into the node's tree; a report and metric for a node that stops applying the masterchain; pending election registrations kept valid through postponed starts; validator disk sizing guidance; `tosctl` packaged for NixOS.
14. Fixes: RaptorQ repair-symbol decoding and refusal of malformed peer symbols; refusal of a signature dictionary that is not in canonical form; a liteserver query cache bounded by the memory it owns; persistent-state and init-block refresh after genesis; absolute validator key expirations preserved by `tosctl`.
15. Verification: the Rust VM and transaction executor reproduce every transaction of the real-epoch replay corpus with complete transaction and account roots; the wider conformance vectors still record open differences between the Rust VM and the C++ VM at version 16 (`test/conformance/docs/tosvm.md`). The C++ node remains the reference implementation. A conformance suite of eleven harnesses with external vectors, chain and archive replay and fuzzing; local benchmark suites for post-quantum throughput and shard scaling.
16. Platforms: Linux on x86-64 and arm64, built on Ubuntu 24.04; release binaries need glibc 2.39 or newer. New for validators: a validator must run on an x86-64 CPU that exposes SHA-NI, SSSE3, SSE4.1 and SSE4.2 (`doc/Validator.md`); the binaries' x86-64-v2 baseline is lower than that, and the node does not check it at start-up. Rust components are built with Rust 1.100.0.
