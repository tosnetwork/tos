## 2026.11-1 Update

Tagged `v2026.11-1`. It follows `v2026.11` and changes how a release is built, published and verified, and which hosts may validate. It changes no consensus rule, price or configuration value; the arm64 implementation of one signature check changes (item 3), its results do not.

No asset is renamed or removed. Additive: `tosctl-linux-<arch>`, a `tosctl` member in `tos-node-linux-<arch>.zip`, `assets` in `release-provenance.json`, and new build-record lines (`slhdsa_sha256`, the `rustc` and `cargo` version lines, `rust_flags`, and the `needed` and `sha256` lines of `tosctl`); read the record by line prefix, not by position.

1. `tosctl` is part of the release: `tosctl-linux-x86_64` and `tosctl-linux-arm64`, built by the node recipe from the tagged commit with the pinned Rust toolchain and the committed `Cargo.lock`, for a fixed CPU baseline, and listed in the same build record as the node binaries. A host that installs from a release needs no Rust toolchain. Beyond the C runtime `tosctl` needs `libssl.so.3`, `libcrypto.so.3` (Ubuntu package `libssl3t64`) and `libgcc_s.so.1`.
2. Every published file except `SHA256SUMS` is attested. The publisher signs build provenance, through Sigstore, for every file `SHA256SUMS` lists, with the identity of the publishing workflow on `main`; publication waits for it. `release-provenance.json`, itself attested, now records under `assets` the SHA-256 of every published asset (every file except itself and `SHA256SUMS`), so the one attested record binds each asset to the tag. Verify with `gh attestation verify release-provenance.json --repo tosnetwork/tos --cert-identity https://github.com/tosnetwork/tos/.github/workflows/create-release.yml@refs/heads/main --source-ref refs/heads/main`, then compare the tag, the commit and the asset digests in it. This is the first release with attestations: the identity string above is the one a run from `main` is expected to carry and has not been observed yet; check it against this release before relying on it. The publisher refuses a run dispatched from another ref than `main`; that is a guard against a mistake, and the control is the pinned ref in the verification command. `v2026.11` has no attestations. See `doc/tos-release-policy.md`, "Attestations".
3. Hardware SHA-256 for the SLH-DSA check on arm64. Linux arm64 builds use the ARMv8 SHA2 instructions when the CPU exposes the AES, PMULL, SHA1 and SHA2 extensions and the portable backend otherwise; the transform is the unmodified file of the project the x86-64 SHA-NI transform already comes from, at the same revision. Results are identical on every backend: the checks compare each hardware path, and the forced portable path, with the unmodified portable implementation and run the signature vectors on both architectures.
4. Validators are permitted by capability, on either architecture: a validator must verify with the hardware SHA-256 backend, on x86-64 (SHA-NI, SSSE3, SSE4.1, SSE4.2) or on arm64 (AES, PMULL, SHA1, SHA2). The portable backend is not allowed for a validator. This replaces the validator rule in item 16 of the 2026.11 update, which allowed x86-64 only; the rest of that item stands, including that the node does not check the backend at start-up. The arm64 figures behind the rule come from one CPU generation on a shared cloud VM; `doc/Validator.md`, "CPU instruction set", has the measurements, their limits and the deployment receipt every validator keeps. **New for every validator, x86-64 included:** the receipt has a fourth step, a time bound: the hardware backend's median on the committed worst-case input must not exceed 360 µs, and a host above it is not allowed. Repeat the receipt after installing this release; its two test programs are not shipped and are built from the release commit (`doc/Validator.md`). The arm64 binaries of `v2026.11` have no hardware backend and must not be used for a validator.
5. The node build of a release refuses to finish unless the hardware SHA-256 backend of its architecture is built in, and its build record names both backend switches (`slhdsa_sha256`).
6. An input built by search to maximise the verifier's work in the SLH-DSA check (3,174 SHA-256 compressions, against 2,214 for the honest signature it was made from; the bound for the parameter set is 3,894, and whether the price covers that bound remains open) is a committed test vector, held to exactly that work by a counted check, and timed on x86-64 and arm64 by the pull-request checks that touch this code (reported, not a gate).
7. Publisher fixes found by the first release: the collection directory no longer collides with a directory of the repository; a published release is deleted only if its tag moved, since deleting an immutable release would make the tag unusable; the release listing is read again before a step refuses.
